# Dzien 1 (2026-07-24) - Podstawy skladni Robot Framework

## 1. Temat dnia
Podstawy skladni Robot Framework - struktura plikow .robot, sekcje, separator kolumn, komentarze.

## 2. Kluczowe zasady i najlepsze praktyki
- Plik .robot dzieli sie na sekcje: *** Settings ***, *** Variables ***, *** Test Cases ***, *** Keywords *** - nazwy sekcji musza byc dokladnie takie.
- Kolumny (argumenty slow kluczowych) rozdziela sie co najmniej dwoma spacjami albo znakiem tabulacji - jedna spacja nie wystarczy i RF potraktuje tekst jako jeden argument.
- Nazwy testow i slow kluczowych pisz w stylu czytelnym dla czlowieka (Title Case, pelne zdania), np. "Zaloguj uzytkownika z poprawnymi danymi" - to jednoczesnie dokumentacja testu.
- Uzywaj "..." (trzy kropki) do kontynuacji dlugiej linii - poprawia czytelnosc w repo i podczas code review.
- Komentarze zaczynaj od # na poczatku linii lub jako osobna kolumna - nie mieszaj kodu i komentarza w tej samej "komorce".

## 3. Przykladowy kod
```robotframework
*** Settings ***
Library           BuiltIn
Documentation     Przykladowy test pokazujacy podstawowa skladnie RF.

*** Variables ***
${URL}            https://example.com
${BROWSER}        chrome

*** Test Cases ***
Sprawdzenie podstawowego dodawania
    [Documentation]    Test weryfikuje dzialanie prostego slowa kluczowego.
    [Tags]    smoke    podstawy
    ${wynik}=    Evaluate    2 + 2
    Should Be Equal As Integers    ${wynik}    4

Test z dluga linia i kontynuacja
    Log Many
    ...    Pierwsza linia logu
    ...    Druga linia logu
    ...    Trzecia linia logu
```

## 4. Najczestsze bledy
- Rozdzielanie argumentow pojedyncza spacja zamiast dwiema - RF zlepia argumenty w jeden string.
- Literowki w nazwach sekcji (np. *** Test Case *** zamiast *** Test Cases ***) - sekcja zostaje zignorowana bez wyraznego bledu.
- Mieszanie tabulacji i spacji w tym samym pliku, co powoduje trudne do zdiagnozowania bledy parsowania.
- Brak [Documentation] i [Tags] - testy staja sie nieczytelne przy wiekszej skali projektu.

## 5. Ulepszenia z AI
- Poproś Claude/Copilot o wygenerowanie szkieletu pliku .robot na podstawie opisu scenariusza w jezyku naturalnym ("napisz test logowania z niepoprawnym haslem").
- Wklej istniejacy plik .robot i poproś AI o wykrycie bledow skladniowych (np. zle odstepy, brakujace sekcje) przed uruchomieniem testu.
- Uzyj AI do konwersji nieformalnych krokow testowych (np. z Jira/user story) na gotowa strukture Test Case + Keywords.
- Poproś o wygenerowanie dokumentacji [Documentation] na podstawie krokow testu, jesli zostala pominieta.

## Zadanie na dzis
Napisz plik .robot z sekcjami Settings, Variables i Test Cases, zawierajacy jeden test, ktory uzywa co najmniej dwoch wbudowanych slow kluczowych (Log, Should Be Equal, Evaluate itp.) oraz poprawnie sformatowana kontynuacje linii (...).

# Dzien 2 (2026-07-25) - Slowa kluczowe wbudowane (BuiltIn)

## 1. Temat dnia
Slowa kluczowe wbudowane z biblioteki BuiltIn - najczesciej uzywane keywordy dostepne w kazdym pliku .robot bez importu.

## 2. Kluczowe zasady i najlepsze praktyki
- Biblioteka BuiltIn jest importowana domyslnie - nie trzeba jej dodawac w sekcji Settings, zawiera m.in. Log, Should Be Equal, Set Variable, Run Keyword If, Evaluate.
- Do porownan uzywaj wlasciwego typu asercji: Should Be Equal (stringi), Should Be Equal As Integers/Numbers (liczby) - porownanie stringa z liczba bez konwersji czesto konczy sie falszywym PASS lub myllacym FAIL.
- Unikaj nadmiernego zagniezdzania Run Keyword If - powyzej 2 warunkow czytelniej jest napisac wlasny Custom Keyword lub uzyc IF/ELSE (nowa skladnia RF 5+).
- Set Variable, Set Test Variable, Set Suite Variable i Set Global Variable maja rozny zasieg - dobierz najwezszy mozliwy, zeby nie "wyciekaly" zmienne miedzy testami.
- Uzywaj Should Contain, Should Match, Should Start With zamiast recznego parsowania stringow - kod jest krotszy i czytelniejszy w log.html.

## 3. Przykladowy kod
```robotframework
*** Test Cases ***
Weryfikacja slow kluczowych BuiltIn
    [Documentation]    Przyklad uzycia popularnych keywordow z biblioteki BuiltIn.
    ${suma}=    Evaluate    10 + 5
    Should Be Equal As Integers    ${suma}    15

    ${status}=    Set Variable    aktywny
    IF    '${status}' == 'aktywny'
        Log    Uzytkownik jest aktywny    console=True
    ELSE
        Fail    Nieoczekiwany status uzytkownika
    END

    ${tekst}=    Set Variable    Robot Framework to super narzedzie
    Should Contain    ${tekst}    Framework
    Should Not Be Empty    ${tekst}

    Run Keyword If    ${suma} > 10    Log    Suma wieksza niz 10
    ...    ELSE    Log    Suma mniejsza lub rowna 10
```

## 4. Najczestsze bledy
- Uzywanie Should Be Equal do porownania liczb bez konwersji typu (np. porownanie ${x} z "5" jako string zamiast liczby).
- Nadmiar zagniezdzonych Run Keyword If zamiast czytelnego IF/ELSE lub osobnego keywordu.
- Nadpisywanie zmiennych globalnych (Set Global Variable) tam, gdzie wystarczy Set Test Variable - powoduje trudne do namierzenia zaleznosci miedzy testami.
- Ignorowanie wartosci zwracanej przez Evaluate/Set Variable i poleganie na efektach ubocznych zamiast jawnych asercji.

## 5. Ulepszenia z AI
- Poproś Claude/Copilot o liste najbardziej przydatnych keywordow BuiltIn do konkretnego scenariusza (np. "jakich slow kluczowych uzyc do walidacji listy stringow").
- Wklej fragment testu z zagniezdzonymi Run Keyword If i poproś AI o refaktoryzacje do czytelnej skladni IF/ELSE.
- Uzyj AI do wygenerowania zestawu asercji (Should Be Equal, Should Contain, Should Match Regexp) na podstawie opisu oczekiwanego zachowania w jezyku naturalnym.
- Poproś o wyjasnienie roznicy miedzy Set Test/Suite/Global Variable w kontekscie konkretnego projektu, gdy nie jest jasne, ktorego uzyc.

## Zadanie na dzis
Napisz test, ktory pobiera wartosc liczbowa przez Evaluate, sprawdza ja warunkiem IF/ELSE, a nastepnie uzywa co najmniej dwoch roznych asercji Should * (np. Should Contain i Should Be Equal As Integers) na wynikach posrednich.

# Dzien 3 (2026-07-26) - Zmienne i ich zasiegi

## 1. Temat dnia
Zmienne w Robot Framework - typy zmiennych (${scalar}, @{list}, &{dict}, %{env}) oraz ich zasiegi (scopes): lokalny, testowy, suite'owy i globalny.

## 2. Kluczowe zasady i najlepsze praktyki
- RF ma cztery typy zmiennych: ${scalar} (pojedyncza wartosc), @{list} (lista), &{dict} (slownik), %{env} (zmienna srodowiskowa) - dobierz typ zgodnie z rzeczywista struktura danych, nie tylko ${} do wszystkiego.
- Zasieg domyslny zmiennej ustawionej przez "${x}=    Keyword" wewnatrz test case'u to zasieg lokalny (tylko biezacy test) - jesli potrzebujesz przekazac wartosc dalej, uzyj Set Test/Suite/Global Variable.
- Hierarchia zasiegow od najwezszego do najszerszego: lokalny (Keyword/Test) -> Set Test Variable -> Set Suite Variable -> Set Global Variable - zawsze wybieraj najwezszy mozliwy, by uniknac wyciekania stanu miedzy testami.
- Zmienne zdefiniowane w sekcji *** Variables *** sa dostepne w calym suite od momentu wczytania pliku - nadpisuj je w razie potrzeby przez wiersz polecen (-v NAZWA:wartosc) zamiast edytowac plik.
- Do zmiennych srodowiskowych i konfiguracyjnych uzywaj %{ZMIENNA_SRODOWISKOWA} lub Get Environment Variable z wartoscia domyslna, zamiast zakladac, ze zmienna zawsze istnieje.

## 3. Przykladowy kod
```robotframework
*** Settings ***
Library           Collections
Library           OperatingSystem

*** Variables ***
${BASE_URL}       https://example.com
@{UZYTKOWNICY}    admin    tester    gosc
&{DANE_LOGOWANIA}    login=admin    haslo=Sekret123

*** Test Cases ***
Zmienne scalar, list i dict
    [Documentation]    Prezentacja roznych typow zmiennych i ich zasiegow.
    Log    Adres bazowy: ${BASE_URL}

    FOR    ${uzytkownik}    IN    @{UZYTKOWNICY}
        Log    Przetwarzam uzytkownika: ${uzytkownik}
    END

    Log    Login: ${DANE_LOGOWANIA}[login]

    ${licznik}=    Set Variable    0
    Set Test Variable    ${licznik}    1
    Set Suite Variable    ${OSTATNI_TEST}    Zmienne scalar, list i dict

Odczyt zmiennej srodowiskowej z wartoscia domyslna
    ${env}=    Get Environment Variable    RF_ENV    default
    Should Not Be Empty    ${env}
    Log    Srodowisko testowe: ${env}
```

## 4. Najczestsze bledy
- Ustawianie zmiennej lokalnie (${x}=    Keyword) i oczekiwanie, ze bedzie widoczna w kolejnym tescie - bez Set Test/Suite Variable znika po zakonczeniu testu.
- Nadmierne uzycie Set Global Variable "na wszelki wypadek" - powoduje trudne do wytropienia zaleznosci i testy, ktore dzialaja tylko w okreslonej kolejnosci.
- Mieszanie typow: dostep do listy jak do zmiennej skalarnej (${UZYTKOWNICY} zamiast @{UZYTKOWNICY} przy iteracji) - RF nie zawsze zglosi to jako blad, ale zachowanie bedzie nieoczekiwane.
- Brak wartosci domyslnej przy odczycie zmiennych srodowiskowych/konfiguracyjnych - test wywala sie z niejasnym bledem na innym srodowisku (np. lokalnie vs CI).

## 5. Ulepszenia z AI
- Poproś Claude/Copilot o przeanalizowanie istniejacego suite'u i wskazanie, gdzie zmienne maja zbyt szeroki zasieg (np. nadmiar Set Global Variable) wraz z propozycja zawezenia.
- Wklej fragment testu z powtarzajacymi sie literalami (URL-e, dane logowania) i poproś AI o wyodrebnienie ich do sekcji *** Variables *** lub pliku resource.
- Uzyj AI do wygenerowania przykladowych danych testowych jako @{list} lub &{dict} na podstawie opisu struktury (np. "wygeneruj slownik z 5 polami uzytkownika").
- Poproś o wyjasnienie, dlaczego konkretna zmienna "nie dziala" w kolejnym tescie/keywordzie - AI szybko wskaze brakujacy Set Test/Suite/Global Variable.

## Zadanie na dzis
Napisz suite z co najmniej dwoma testami: w pierwszym ustaw zmienna przez Set Suite Variable, a w drugim odczytaj i zweryfikuj jej wartosc. Dodatkowo zdefiniuj zmienna typu @{list} i &{dict} w sekcji *** Variables *** i uzyj obu w petli FOR oraz przy dostepie do konkretnego klucza slownika.

# Dzien 4 (2026-07-27) - Test/Suite/Task setup i teardown

## 1. Temat dnia
Setup i teardown na poziomie testu, suite'u i taska (RPA) - jak przygotowywac srodowisko przed testami i sprzatac po nich niezaleznie od wyniku.

## 2. Kluczowe zasady i najlepsze praktyki
- Suite Setup/Suite Teardown (sekcja *** Settings ***) uruchamiaja sie raz na caly plik/suite - idealne do kosztownych operacji, np. logowanie, start serwera, otwarcie przegladarki.
- Test Setup/Test Teardown w *** Settings *** ustawiaja domyslne zachowanie dla WSZYSTKICH testow w pliku; [Setup]/[Teardown] zdefiniowany bezposrednio przy tescie NADPISUJE domyslny, a nie dodaje sie do niego.
- Teardown wykonuje sie zawsze - rowniez wtedy, gdy test/suite zakonczyl sie bledem, timeoutem lub Fatal Error - dlatego to wlasciwe miejsce na zamykanie zasobow (przegladarka, polaczenia, pliki tymczasowe).
- Do laczenia kilku slow kluczowych w jednym [Setup]/[Teardown] uzywaj Run Keywords ... AND ..., a przy wiekszej liczbie krokow lepiej wydzielic osobny Custom Keyword - jest czytelniej w log.html.
- W teardownie stosuj Run Keyword If Test Failed (zrzut ekranu, dodatkowe logi tylko przy porazce) oraz Run Keyword And Ignore Error dla krokow sprzatajacych, ktore nie powinny przerywac kolejnych krokow czyszczenia.
- W RPA (Robot Framework jako framework do automatyzacji procesow) analogiczne role pelnia Task Setup/Task Teardown - dzialaja identycznie jak Test Setup/Teardown, ale w kontekscie *** Tasks ***.

## 3. Przykladowy kod
```robotframework
*** Settings ***
Library           SeleniumLibrary
Suite Setup       Otworz przegladarke i zaloguj
Suite Teardown    Zamknij wszystkie przegladarki
Test Setup        Przejdz na strone glowna
Test Teardown     Wykonaj sprzatanie po tescie

*** Test Cases ***
Test z domyslnym teardown
    [Documentation]    Korzysta z Test Setup/Teardown zdefiniowanych w Settings.
    Page Should Contain    Witaj

Test z wlasnym teardown nadpisujacym domyslny
    [Teardown]    Run Keywords    Zrzut ekranu przy bledzie    AND    Wyloguj uzytkownika
    Fail    Celowy blad do demonstracji dzialania teardown

*** Keywords ***
Otworz przegladarke i zaloguj
    Open Browser    https://example.com    chrome
    Input Text    id=login    admin
    Input Text    id=haslo    Sekret123
    Click Button    Zaloguj

Zamknij wszystkie przegladarki
    Close All Browsers

Przejdz na strone glowna
    Go To    https://example.com/dashboard

Wykonaj sprzatanie po tescie
    Run Keyword If Test Failed    Zrzut ekranu przy bledzie
    Run Keyword And Ignore Error    Log    Test zakonczony, sprzatanie wykonane

Zrzut ekranu przy bledzie
    Capture Page Screenshot

Wyloguj uzytkownika
    Click Button    Wyloguj
```

## 4. Najczestsze bledy
- Zalozenie, ze [Teardown] przy tescie "dolacza sie" do Test Teardown z Settings - w rzeczywistosci go zastepuje, przez co domyslne sprzatanie po cichu przestaje dzialac dla tego testu.
- Wykonywanie zrzutow ekranu/dodatkowych logow w kazdym teardownie bez warunku Run Keyword If Test Failed - logi robia sie ogromne i trudne do przegladania.
- Niestabilny teardown, ktory sam rzuca wyjatkiem (np. probuje zamknac przegladarke, ktora nigdy sie nie otworzyla) - warto zabezpieczyc krytyczne kroki sprzatania przez Run Keyword And Ignore Error.
- Umieszczanie w Suite Setup logiki, ktora powinna byc w Test Setup (np. logowanie tego samego uzytkownika przed kazdym testem) - powoduje, ze testy dzieda sie od wspolnego, mutowalnego stanu i nie sa od siebie niezalezne.

## 5. Ulepszenia z AI
- Poproś Claude/Copilot o przeanalizowanie suite'u pod katem brakujacych teardownow - np. gdzie Open Browser/Connect nie ma odpowiadajacego Close/Disconnect.
- Wklej test konczacy sie bledem w teardownie i poproś AI o dodanie Run Keyword And Ignore Error tam, gdzie to bezpieczne, bez ukrywania prawdziwych bledow testu.
- Uzyj AI do wygenerowania wspolnego Custom Keyword laczacego kilka krokow sprzatania (np. wylogowanie + zamkniecie przegladarki + usuniecie plikow tymczasowych) na podstawie opisu w jezyku naturalnym.
- Poproś AI o wyjasnienie, dlaczego dany test "traci" domyslny teardown - czesto wystarczy wskazac, ze [Teardown] przy tescie nadpisuje Test Teardown z Settings.

## Zadanie na dzis
Napisz suite z Suite Setup/Suite Teardown (np. symulowane otwarcie/zamkniecie "polaczenia" przez Log) oraz Test Setup/Test Teardown w Settings. Dodaj dwa testy: pierwszy niech korzysta z domyslnego teardown, a drugi niech ma wlasny [Teardown] uzywajacy Run Keyword If Test Failed do warunkowego logowania dodatkowych informacji.
