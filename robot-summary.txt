# Dzien 1 (2026-07-24) - Podstawy skladni Robot Framework

## 1. Temat dnia
Podstawy skladni Robot Framework - struktura plikow .robot, sekcje, separator kolumn, komentarze.

## 2. Kluczowe zasady i najlepsze praktyki
- Plik .robot dzieli sie na sekcje: *** Settings ***, *** Variables ***, *** Test Cases ***, *** Keywords *** - nazwy sekcji musza byc dokladnie takie.
- Kolumny (argumenty slow kluczowych) rozdziela sie co najmniej dwoma spacjami albo znakiem tabulacji - jedna spacja nie wystarczy i RF potraktuje tekst jako jeden argument.
- Nazwy testow i slow kluczowych pisz w stylu czytelnym dla czlowieka (Title Case, pelne zdania), np. "Zaloguj uzytkownika z poprawnymi danymi" - to jednoczesnie dokumentacja testu.
- Uzywaj "..." (trzy kropki) do kontynuacji dlugiej linii - poprawia czytelnosc w repo i podczas code review.
- Komentarze zaczynaj od # na poczatku linii lub jako osobna kolumna - nie mieszaj kodu i komentarza w tej samej "komorce".

## 3. Przykladowy kod
```robotframework
*** Settings ***
Library           BuiltIn
Documentation     Przykladowy test pokazujacy podstawowa skladnie RF.

*** Variables ***
${URL}            https://example.com
${BROWSER}        chrome

*** Test Cases ***
Sprawdzenie podstawowego dodawania
    [Documentation]    Test weryfikuje dzialanie prostego slowa kluczowego.
    [Tags]    smoke    podstawy
    ${wynik}=    Evaluate    2 + 2
    Should Be Equal As Integers    ${wynik}    4

Test z dluga linia i kontynuacja
    Log Many
    ...    Pierwsza linia logu
    ...    Druga linia logu
    ...    Trzecia linia logu
```

## 4. Najczestsze bledy
- Rozdzielanie argumentow pojedyncza spacja zamiast dwiema - RF zlepia argumenty w jeden string.
- Literowki w nazwach sekcji (np. *** Test Case *** zamiast *** Test Cases ***) - sekcja zostaje zignorowana bez wyraznego bledu.
- Mieszanie tabulacji i spacji w tym samym pliku, co powoduje trudne do zdiagnozowania bledy parsowania.
- Brak [Documentation] i [Tags] - testy staja sie nieczytelne przy wiekszej skali projektu.

## 5. Ulepszenia z AI
- Poproś Claude/Copilot o wygenerowanie szkieletu pliku .robot na podstawie opisu scenariusza w jezyku naturalnym ("napisz test logowania z niepoprawnym haslem").
- Wklej istniejacy plik .robot i poproś AI o wykrycie bledow skladniowych (np. zle odstepy, brakujace sekcje) przed uruchomieniem testu.
- Uzyj AI do konwersji nieformalnych krokow testowych (np. z Jira/user story) na gotowa strukture Test Case + Keywords.
- Poproś o wygenerowanie dokumentacji [Documentation] na podstawie krokow testu, jesli zostala pominieta.

## Zadanie na dzis
Napisz plik .robot z sekcjami Settings, Variables i Test Cases, zawierajacy jeden test, ktory uzywa co najmniej dwoch wbudowanych slow kluczowych (Log, Should Be Equal, Evaluate itp.) oraz poprawnie sformatowana kontynuacje linii (...).

# Dzien 2 (2026-07-25) - Slowa kluczowe wbudowane (BuiltIn)

## 1. Temat dnia
Slowa kluczowe wbudowane z biblioteki BuiltIn - najczesciej uzywane keywordy dostepne w kazdym pliku .robot bez importu.

## 2. Kluczowe zasady i najlepsze praktyki
- Biblioteka BuiltIn jest importowana domyslnie - nie trzeba jej dodawac w sekcji Settings, zawiera m.in. Log, Should Be Equal, Set Variable, Run Keyword If, Evaluate.
- Do porownan uzywaj wlasciwego typu asercji: Should Be Equal (stringi), Should Be Equal As Integers/Numbers (liczby) - porownanie stringa z liczba bez konwersji czesto konczy sie falszywym PASS lub myllacym FAIL.
- Unikaj nadmiernego zagniezdzania Run Keyword If - powyzej 2 warunkow czytelniej jest napisac wlasny Custom Keyword lub uzyc IF/ELSE (nowa skladnia RF 5+).
- Set Variable, Set Test Variable, Set Suite Variable i Set Global Variable maja rozny zasieg - dobierz najwezszy mozliwy, zeby nie "wyciekaly" zmienne miedzy testami.
- Uzywaj Should Contain, Should Match, Should Start With zamiast recznego parsowania stringow - kod jest krotszy i czytelniejszy w log.html.

## 3. Przykladowy kod
```robotframework
*** Test Cases ***
Weryfikacja slow kluczowych BuiltIn
    [Documentation]    Przyklad uzycia popularnych keywordow z biblioteki BuiltIn.
    ${suma}=    Evaluate    10 + 5
    Should Be Equal As Integers    ${suma}    15

    ${status}=    Set Variable    aktywny
    IF    '${status}' == 'aktywny'
        Log    Uzytkownik jest aktywny    console=True
    ELSE
        Fail    Nieoczekiwany status uzytkownika
    END

    ${tekst}=    Set Variable    Robot Framework to super narzedzie
    Should Contain    ${tekst}    Framework
    Should Not Be Empty    ${tekst}

    Run Keyword If    ${suma} > 10    Log    Suma wieksza niz 10
    ...    ELSE    Log    Suma mniejsza lub rowna 10
```

## 4. Najczestsze bledy
- Uzywanie Should Be Equal do porownania liczb bez konwersji typu (np. porownanie ${x} z "5" jako string zamiast liczby).
- Nadmiar zagniezdzonych Run Keyword If zamiast czytelnego IF/ELSE lub osobnego keywordu.
- Nadpisywanie zmiennych globalnych (Set Global Variable) tam, gdzie wystarczy Set Test Variable - powoduje trudne do namierzenia zaleznosci miedzy testami.
- Ignorowanie wartosci zwracanej przez Evaluate/Set Variable i poleganie na efektach ubocznych zamiast jawnych asercji.

## 5. Ulepszenia z AI
- Poproś Claude/Copilot o liste najbardziej przydatnych keywordow BuiltIn do konkretnego scenariusza (np. "jakich slow kluczowych uzyc do walidacji listy stringow").
- Wklej fragment testu z zagniezdzonymi Run Keyword If i poproś AI o refaktoryzacje do czytelnej skladni IF/ELSE.
- Uzyj AI do wygenerowania zestawu asercji (Should Be Equal, Should Contain, Should Match Regexp) na podstawie opisu oczekiwanego zachowania w jezyku naturalnym.
- Poproś o wyjasnienie roznicy miedzy Set Test/Suite/Global Variable w kontekscie konkretnego projektu, gdy nie jest jasne, ktorego uzyc.

## Zadanie na dzis
Napisz test, ktory pobiera wartosc liczbowa przez Evaluate, sprawdza ja warunkiem IF/ELSE, a nastepnie uzywa co najmniej dwoch roznych asercji Should * (np. Should Contain i Should Be Equal As Integers) na wynikach posrednich.

# Dzien 3 (2026-07-26) - Zmienne i ich zasiegi

## 1. Temat dnia
Zmienne w Robot Framework - typy zmiennych (${scalar}, @{list}, &{dict}, %{env}) oraz ich zasiegi (scopes): lokalny, testowy, suite'owy i globalny.

## 2. Kluczowe zasady i najlepsze praktyki
- RF ma cztery typy zmiennych: ${scalar} (pojedyncza wartosc), @{list} (lista), &{dict} (slownik), %{env} (zmienna srodowiskowa) - dobierz typ zgodnie z rzeczywista struktura danych, nie tylko ${} do wszystkiego.
- Zasieg domyslny zmiennej ustawionej przez "${x}=    Keyword" wewnatrz test case'u to zasieg lokalny (tylko biezacy test) - jesli potrzebujesz przekazac wartosc dalej, uzyj Set Test/Suite/Global Variable.
- Hierarchia zasiegow od najwezszego do najszerszego: lokalny (Keyword/Test) -> Set Test Variable -> Set Suite Variable -> Set Global Variable - zawsze wybieraj najwezszy mozliwy, by uniknac wyciekania stanu miedzy testami.
- Zmienne zdefiniowane w sekcji *** Variables *** sa dostepne w calym suite od momentu wczytania pliku - nadpisuj je w razie potrzeby przez wiersz polecen (-v NAZWA:wartosc) zamiast edytowac plik.
- Do zmiennych srodowiskowych i konfiguracyjnych uzywaj %{ZMIENNA_SRODOWISKOWA} lub Get Environment Variable z wartoscia domyslna, zamiast zakladac, ze zmienna zawsze istnieje.

## 3. Przykladowy kod
```robotframework
*** Settings ***
Library           Collections
Library           OperatingSystem

*** Variables ***
${BASE_URL}       https://example.com
@{UZYTKOWNICY}    admin    tester    gosc
&{DANE_LOGOWANIA}    login=admin    haslo=Sekret123

*** Test Cases ***
Zmienne scalar, list i dict
    [Documentation]    Prezentacja roznych typow zmiennych i ich zasiegow.
    Log    Adres bazowy: ${BASE_URL}

    FOR    ${uzytkownik}    IN    @{UZYTKOWNICY}
        Log    Przetwarzam uzytkownika: ${uzytkownik}
    END

    Log    Login: ${DANE_LOGOWANIA}[login]

    ${licznik}=    Set Variable    0
    Set Test Variable    ${licznik}    1
    Set Suite Variable    ${OSTATNI_TEST}    Zmienne scalar, list i dict

Odczyt zmiennej srodowiskowej z wartoscia domyslna
    ${env}=    Get Environment Variable    RF_ENV    default
    Should Not Be Empty    ${env}
    Log    Srodowisko testowe: ${env}
```

## 4. Najczestsze bledy
- Ustawianie zmiennej lokalnie (${x}=    Keyword) i oczekiwanie, ze bedzie widoczna w kolejnym tescie - bez Set Test/Suite Variable znika po zakonczeniu testu.
- Nadmierne uzycie Set Global Variable "na wszelki wypadek" - powoduje trudne do wytropienia zaleznosci i testy, ktore dzialaja tylko w okreslonej kolejnosci.
- Mieszanie typow: dostep do listy jak do zmiennej skalarnej (${UZYTKOWNICY} zamiast @{UZYTKOWNICY} przy iteracji) - RF nie zawsze zglosi to jako blad, ale zachowanie bedzie nieoczekiwane.
- Brak wartosci domyslnej przy odczycie zmiennych srodowiskowych/konfiguracyjnych - test wywala sie z niejasnym bledem na innym srodowisku (np. lokalnie vs CI).

## 5. Ulepszenia z AI
- Poproś Claude/Copilot o przeanalizowanie istniejacego suite'u i wskazanie, gdzie zmienne maja zbyt szeroki zasieg (np. nadmiar Set Global Variable) wraz z propozycja zawezenia.
- Wklej fragment testu z powtarzajacymi sie literalami (URL-e, dane logowania) i poproś AI o wyodrebnienie ich do sekcji *** Variables *** lub pliku resource.
- Uzyj AI do wygenerowania przykladowych danych testowych jako @{list} lub &{dict} na podstawie opisu struktury (np. "wygeneruj slownik z 5 polami uzytkownika").
- Poproś o wyjasnienie, dlaczego konkretna zmienna "nie dziala" w kolejnym tescie/keywordzie - AI szybko wskaze brakujacy Set Test/Suite/Global Variable.

## Zadanie na dzis
Napisz suite z co najmniej dwoma testami: w pierwszym ustaw zmienna przez Set Suite Variable, a w drugim odczytaj i zweryfikuj jej wartosc. Dodatkowo zdefiniuj zmienna typu @{list} i &{dict} w sekcji *** Variables *** i uzyj obu w petli FOR oraz przy dostepie do konkretnego klucza slownika.

# Dzien 4 (2026-07-27) - Test/Suite/Task setup i teardown

## 1. Temat dnia
Setup i teardown na poziomie testu, suite'u i taska (RPA) - jak przygotowywac srodowisko przed testami i sprzatac po nich niezaleznie od wyniku.

## 2. Kluczowe zasady i najlepsze praktyki
- Suite Setup/Suite Teardown (sekcja *** Settings ***) uruchamiaja sie raz na caly plik/suite - idealne do kosztownych operacji, np. logowanie, start serwera, otwarcie przegladarki.
- Test Setup/Test Teardown w *** Settings *** ustawiaja domyslne zachowanie dla WSZYSTKICH testow w pliku; [Setup]/[Teardown] zdefiniowany bezposrednio przy tescie NADPISUJE domyslny, a nie dodaje sie do niego.
- Teardown wykonuje sie zawsze - rowniez wtedy, gdy test/suite zakonczyl sie bledem, timeoutem lub Fatal Error - dlatego to wlasciwe miejsce na zamykanie zasobow (przegladarka, polaczenia, pliki tymczasowe).
- Do laczenia kilku slow kluczowych w jednym [Setup]/[Teardown] uzywaj Run Keywords ... AND ..., a przy wiekszej liczbie krokow lepiej wydzielic osobny Custom Keyword - jest czytelniej w log.html.
- W teardownie stosuj Run Keyword If Test Failed (zrzut ekranu, dodatkowe logi tylko przy porazce) oraz Run Keyword And Ignore Error dla krokow sprzatajacych, ktore nie powinny przerywac kolejnych krokow czyszczenia.
- W RPA (Robot Framework jako framework do automatyzacji procesow) analogiczne role pelnia Task Setup/Task Teardown - dzialaja identycznie jak Test Setup/Teardown, ale w kontekscie *** Tasks ***.

## 3. Przykladowy kod
```robotframework
*** Settings ***
Library           SeleniumLibrary
Suite Setup       Otworz przegladarke i zaloguj
Suite Teardown    Zamknij wszystkie przegladarki
Test Setup        Przejdz na strone glowna
Test Teardown     Wykonaj sprzatanie po tescie

*** Test Cases ***
Test z domyslnym teardown
    [Documentation]    Korzysta z Test Setup/Teardown zdefiniowanych w Settings.
    Page Should Contain    Witaj

Test z wlasnym teardown nadpisujacym domyslny
    [Teardown]    Run Keywords    Zrzut ekranu przy bledzie    AND    Wyloguj uzytkownika
    Fail    Celowy blad do demonstracji dzialania teardown

*** Keywords ***
Otworz przegladarke i zaloguj
    Open Browser    https://example.com    chrome
    Input Text    id=login    admin
    Input Text    id=haslo    Sekret123
    Click Button    Zaloguj

Zamknij wszystkie przegladarki
    Close All Browsers

Przejdz na strone glowna
    Go To    https://example.com/dashboard

Wykonaj sprzatanie po tescie
    Run Keyword If Test Failed    Zrzut ekranu przy bledzie
    Run Keyword And Ignore Error    Log    Test zakonczony, sprzatanie wykonane

Zrzut ekranu przy bledzie
    Capture Page Screenshot

Wyloguj uzytkownika
    Click Button    Wyloguj
```

## 4. Najczestsze bledy
- Zalozenie, ze [Teardown] przy tescie "dolacza sie" do Test Teardown z Settings - w rzeczywistosci go zastepuje, przez co domyslne sprzatanie po cichu przestaje dzialac dla tego testu.
- Wykonywanie zrzutow ekranu/dodatkowych logow w kazdym teardownie bez warunku Run Keyword If Test Failed - logi robia sie ogromne i trudne do przegladania.
- Niestabilny teardown, ktory sam rzuca wyjatkiem (np. probuje zamknac przegladarke, ktora nigdy sie nie otworzyla) - warto zabezpieczyc krytyczne kroki sprzatania przez Run Keyword And Ignore Error.
- Umieszczanie w Suite Setup logiki, ktora powinna byc w Test Setup (np. logowanie tego samego uzytkownika przed kazdym testem) - powoduje, ze testy dzieda sie od wspolnego, mutowalnego stanu i nie sa od siebie niezalezne.

## 5. Ulepszenia z AI
- Poproś Claude/Copilot o przeanalizowanie suite'u pod katem brakujacych teardownow - np. gdzie Open Browser/Connect nie ma odpowiadajacego Close/Disconnect.
- Wklej test konczacy sie bledem w teardownie i poproś AI o dodanie Run Keyword And Ignore Error tam, gdzie to bezpieczne, bez ukrywania prawdziwych bledow testu.
- Uzyj AI do wygenerowania wspolnego Custom Keyword laczacego kilka krokow sprzatania (np. wylogowanie + zamkniecie przegladarki + usuniecie plikow tymczasowych) na podstawie opisu w jezyku naturalnym.
- Poproś AI o wyjasnienie, dlaczego dany test "traci" domyslny teardown - czesto wystarczy wskazac, ze [Teardown] przy tescie nadpisuje Test Teardown z Settings.

## Zadanie na dzis
Napisz suite z Suite Setup/Suite Teardown (np. symulowane otwarcie/zamkniecie "polaczenia" przez Log) oraz Test Setup/Test Teardown w Settings. Dodaj dwa testy: pierwszy niech korzysta z domyslnego teardown, a drugi niech ma wlasny [Teardown] uzywajacy Run Keyword If Test Failed do warunkowego logowania dodatkowych informacji.

# Dzien 5 (2026-07-28) - Biblioteki standardowe (Collections, String, OperatingSystem, DateTime)

## 1. Temat dnia
Wbudowane biblioteki standardowe Robot Framework inne niz BuiltIn: Collections (listy/slowniki), String (operacje na tekscie), OperatingSystem (pliki i system) oraz DateTime (data i czas).

## 2. Kluczowe zasady i najlepsze praktyki
- Kazda z tych bibliotek wymaga jawnego importu w sekcji *** Settings *** (Library Collections / String / OperatingSystem / DateTime) - w przeciwienstwie do BuiltIn nie sa dostepne domyslnie.
- Collections udostepnia dedykowane asercje dla list/slownikow (Lists Should Be Equal, Dictionary Should Contain Key) - sa czytelniejsze i daja lepsze komunikaty bledow niz porownywanie recznie przez Should Be Equal.
- String sluzy do manipulacji tekstem (Split String, Strip String, Get Substring, Convert To Upper Case) - unikaj laczenia jej z zewnetrznymi skryptami tam, gdzie wystarczy gotowy keyword.
- OperatingSystem daje dostep do plikow/katalogow/zmiennych srodowiskowych (Create File, Remove File, Directory Should Exist) - przydatne przy testach RPA i przygotowywaniu danych wejsciowych/wyjsciowych.
- DateTime pozwala liczyc i formatowac daty (Get Current Date, Subtract Time From Date, Convert Date) - zawsze podawaj jawny format i strefe czasowa, zeby testy byly powtarzalne niezaleznie od maszyny CI.
- Wybieraj biblioteke adekwatnie do typu danych: Collections dla struktur (list/dict), String dla surowego tekstu - mieszanie ich tam, gdzie jedna wystarczy, zwieksza zlozonosc testu.

## 3. Przykladowy kod
```robotframework
*** Settings ***
Library           Collections
Library           String
Library           OperatingSystem
Library           DateTime

*** Test Cases ***
Operacje na liscie i slowniku
    [Documentation]    Przyklad uzycia biblioteki Collections.
    @{owoce}=    Create List    jablko    gruszka    banan
    Append To List    ${owoce}    pomarancza
    Lists Should Be Equal    ${owoce}    ${{['jablko', 'gruszka', 'banan', 'pomarancza']}}

    &{dane}=    Create Dictionary    imie=Jan    wiek=30
    Dictionary Should Contain Key    ${dane}    imie
    Set To Dictionary    ${dane}    miasto=Warszawa

Operacje tekstowe i plikowe
    [Documentation]    Przyklad uzycia bibliotek String i OperatingSystem.
    ${tekst}=    Set Variable    Robot Framework, wersja 7
    ${czesci}=    Split String    ${tekst}    ,
    ${wielkie}=    Convert To Upper Case    ${tekst}
    Should Contain    ${wielkie}    ROBOT

    Create File    ${OUTPUT_DIR}/raport.txt    Wynik testu: OK
    File Should Exist    ${OUTPUT_DIR}/raport.txt
    ${zawartosc}=    Get File    ${OUTPUT_DIR}/raport.txt
    Should Contain    ${zawartosc}    OK

Operacje na dacie i czasie
    [Documentation]    Przyklad uzycia biblioteki DateTime.
    ${dzis}=    Get Current Date    result_format=%Y-%m-%d
    ${za_tydzien}=    Add Time To Date    ${dzis}    7 days    result_format=%Y-%m-%d
    Log    Dzisiaj: ${dzis}, za tydzien: ${za_tydzien}
```

## 4. Najczestsze bledy
- Uzywanie keywordow z Collections/String/DateTime bez importu odpowiedniej biblioteki - RF zglosi blad "No keyword with name X found", co bywa mylone z literowka w nazwie.
- Porownywanie list/slownikow przez Should Be Equal zamiast Lists Should Be Equal/Dictionaries Should Be Equal - kolejnosc elementow lub typ danych powoduje falszywe FAIL trudne do zdiagnozowania.
- Zakladanie stalego formatu daty zwracanego przez Get Current Date bez podania result_format - test dziala inaczej lokalnie i na serwerze CI w innej strefie czasowej.
- Tworzenie plikow testowych bezposrednio w katalogu projektu zamiast w ${OUTPUT_DIR} - zasmieca repozytorium i utrudnia sprzatanie po testach.

## 5. Ulepszenia z AI
- Poproś Claude/Copilot o wskazanie, ktora biblioteka standardowa (Collections/String/OperatingSystem/DateTime) pasuje do danego zadania, gdy nie jest oczywiste, gdzie szukac keywordu.
- Wklej fragment testu porownujacego listy/slowniki przez Should Be Equal i poproś AI o refaktoryzacje do dedykowanych keywordow z Collections.
- Uzyj AI do wygenerowania przykladowych danych testowych (listy, slowniki, teksty, daty) na podstawie opisu struktury w jezyku naturalnym.
- Poproś AI o wyjasnienie komunikatu bledu "No keyword with name X found" - czesto szybko wskaze brakujacy import biblioteki.

## Zadanie na dzis
Napisz test, ktory: utworzy liste i slownik przez Collections i zweryfikuje ich zawartosc dedykowanymi keywordami, podzieli tekst na czesci przez Split String z biblioteki String, zapisze wynik do pliku w ${OUTPUT_DIR} przez OperatingSystem, a na koniec obliczy date za 7 dni od dzisiaj przez DateTime.

# DZIEN 6: TESTY WEBOWE - SELENIUMLIBRARY / BROWSER LIBRARY (PLAYWRIGHT)
Data: 2026-07-29 (sroda)
================================================================================

## 1. Temat dnia
Automatyzacja testow webowych w Robot Framework - klasyczna **SeleniumLibrary**
oraz nowoczesna **Browser Library** oparta na Playwright. Skupiamy sie glownie
na Browser Library jako aktualnie rekomendowanym wyborze dla nowych projektow.

## 2. Kluczowe zasady i najlepsze praktyki
- Wybieraj **Browser Library (Playwright)** do nowych projektow - dziala szybciej,
  ma wbudowane auto-waity (nie trzeba recznie robic Wait Until Element Is Visible
  tak czesto jak w Selenium) i lepiej obsluguje nowoczesne SPA.
- Uzywaj **selektorow tekstowych/CSS/testid** zamiast kruchych XPath opartych na
  strukturze DOM - `"css=[data-testid=login-button]"` przetrwa refaktoryzacje UI.
- Zawsze otwieraj przegladarke w `Suite Setup` i zamykaj w `Suite Teardown`
  (`New Browser` / `Close Browser`), a nowa strone (`New Page`) per test, jesli
  testy maja byc od siebie niezalezne.
- Stosuj **Page Object Pattern** - trzymaj lokalizatory i akcje na danej stronie
  w osobnym Resource file, testy nie powinny znac szczegolow selektorow.
- Korzystaj z wbudowanych auto-waitow Browser Library zamiast `Sleep` -
  `Click`, `Fill Text` same czekaja az element bedzie interaktywny.

## 3. Przyklad kodu (.robot)
```robotframework
*** Settings ***
Library    Browser
Suite Setup       New Browser    chromium    headless=true
Suite Teardown    Close Browser
Test Setup        New Page    https://example.com/login

*** Variables ***
${LOGIN_INPUT}      css=#username
${PASSWORD_INPUT}    css=#password
${LOGIN_BUTTON}     css=[data-testid=login-button]
${WELCOME_TEXT}     css=.welcome-message

*** Test Cases ***
Poprawne logowanie uzytkownika
    [Documentation]    Sprawdza logowanie z prawidlowymi danymi.
    [Tags]    web    smoke
    Fill Text    ${LOGIN_INPUT}    jan.kowalski
    Fill Text    ${PASSWORD_INPUT}    TajneHaslo123
    Click    ${LOGIN_BUTTON}
    Get Text    ${WELCOME_TEXT}    contains    Witaj, Jan

Blokada logowania przy pustym hasle
    [Documentation]    Weryfikuje komunikat bledu przy braku hasla.
    [Tags]    web    negative
    Fill Text    ${LOGIN_INPUT}    jan.kowalski
    Click    ${LOGIN_BUTTON}
    Get Text    css=.error-message    ==    Haslo jest wymagane
```

Rownowaznik w SeleniumLibrary (dla porownania):
```robotframework
*** Settings ***
Library    SeleniumLibrary

*** Test Cases ***
Logowanie - SeleniumLibrary
    Open Browser    https://example.com/login    chrome
    Input Text    id=username    jan.kowalski
    Input Password    id=password    TajneHaslo123
    Click Button    css=[data-testid=login-button]
    Wait Until Element Is Visible    css=.welcome-message    timeout=5s

    [Teardown]    Close Browser
```

## 4. Najczestsze bledy
- Uzywanie `Sleep` zamiast auto-waitow lub `Wait Until ...` - testy sa wolne

- Twarde XPath typu `//div[3]/div[2]/span` - lamie sie przy kazdej zmianie

- Mieszanie SeleniumLibrary i Browser Library w jednym pliku testowym bez
  wyraznego powodu - roznia sie skladnia keywordow (np. Click vs Click Button)

- Testowanie na jednej przegladarce i zakladanie, ze wynik bedzie identyczny

# Dzien 7 (2026-07-30, czwartek) - RequestsLibrary do testow API

## 1. Temat dnia
Testowanie API (REST) w Robot Framework za pomoca biblioteki RequestsLibrary -
sesje HTTP, wysylanie zadan GET/POST/PUT/DELETE oraz walidacja odpowiedzi JSON.

## 2. Kluczowe zasady i najlepsze praktyki
- Zawsze zaczynaj od `Create Session` z nazwa i adresem bazowym (base URL) -
  pozwala to potem odwolywac sie tylko do sciezek wzglednych (`/posts`) zamiast
  powtarzac pelny adres URL w kazdym zadaniu.
- Preferuj nowsze keywordy `GET On Session`, `POST On Session`, `PUT On Session`,
  `DELETE On Session` (dzialajace na sesji) zamiast starszych `Get Request`/
  `Post Request` bez sesji - latwiej zarzadzac wspolnymi naglowkami i auth.
- Uzywaj parametru `expected_status` zamiast recznego sprawdzania kodu - RF
  od razu zglosi czytelny blad, jesli API zwroci inny status niz oczekiwany
  (np. `expected_status=200` albo `expected_status=201`).
- Odpowiedz (`response`) to obiekt Pythona - dostep do danych przez
  `${response.json()}`, `${response.status_code}`, `${response.text}`; do
  walidacji struktury JSON korzystaj z biblioteki Collections
  (`Dictionary Should Contain Key`, `Get From Dictionary`).
- Tokeny, klucze API i dane logowania trzymaj w zmiennych srodowiskowych lub
  pliku konfiguracyjnym (`%{API_TOKEN}`), nigdy jako literal w pliku .robot -
  szczegolnie jesli repo jest publiczne.
- Ustawiaj rozsadny `timeout` przy tworzeniu sesji, zeby test nie wisial
  w nieskonczonosc przy niedostepnym serwerze/API.

## 3. Przykladowy kod
```robotframework
*** Settings ***
Library           RequestsLibrary
Library           Collections

*** Variables ***
${BASE_URL}       https://jsonplaceholder.typicode.com

*** Test Cases ***
Pobranie listy postow (GET)
    [Documentation]    Test pobiera liste zasobow i weryfikuje odpowiedz.
    [Tags]    api    smoke
    Create Session    jsonplaceholder    ${BASE_URL}    timeout=10
    ${response}=    GET On Session    jsonplaceholder    /posts    expected_status=200
    Should Be Equal As Integers    ${response.status_code}    200
    ${liczba}=    Get Length    ${response.json()}
    Should Be True    ${liczba} > 0

Utworzenie nowego zasobu (POST)
    [Documentation]    Test wysyla dane JSON i weryfikuje utworzenie zasobu.
    [Tags]    api
    Create Session    jsonplaceholder    ${BASE_URL}    timeout=10
    &{dane}=    Create Dictionary    title=Testowy post    body=Tresc testowa    userId=1
    ${response}=    POST On Session    jsonplaceholder    /posts    json=${dane}    expected_status=201
    Dictionary Should Contain Key    ${response.json()}    id
    Should Be Equal    ${response.json()}[title]    Testowy post

Obsluga bledu 404 (negatywny scenariusz)
    [Documentation]    Sprawdza reakcje API na nieistniejacy zasob.
    [Tags]    api    negative
    Create Session    jsonplaceholder    ${BASE_URL}    timeout=10
    ${response}=    GET On Session    jsonplaceholder    /posts/99999    expected_status=404
    Should Be Equal As Integers    ${response.status_code}    404
```

## 4. Najczestsze bledy
- Uzywanie starszych keywordow bez sesji (`Get Request`, `Post Request`) tam,
  gdzie lepiej pasuje sesja z `Create Session` - trudniej wtedy zarzadzac
  wspolnymi naglowkami (np. tokenem auth) dla wielu zadan w tym samym pliku.
- Brak `expected_status` i poleganie tylko na tym, ze RF sam zglosi wyjatek -
  bez jawnego assercji trudno odroznic blad testu od faktycznej awarii API.
- Zakladanie, ze klucz zawsze istnieje w odpowiedzi JSON (`${response.json()}[klucz]`)
  bez wczesniejszej weryfikacji `Dictionary Should Contain Key` - nieczytelny
  KeyError zamiast jasnego komunikatu bledu.
- Hardkodowanie tokenow/API keys bezposrednio w pliku .robot zamiast w
  zmiennych srodowiskowych lub bezpiecznym pliku konfiguracyjnym.
- Brak `timeout` przy `Create Session` - test moze wisiec bardzo dlugo, gdy
  API nie odpowiada, zamiast szybko zakonczyc sie czytelnym bledem.

## 5. Ulepszenia z AI
- Poproś Claude/Copilot o wygenerowanie testow RequestsLibrary na podstawie
  specyfikacji OpenAPI/Swagger danego API (endpointy, metody, kody statusow).
- Wklej przykladowa odpowiedz JSON z API i poproś AI o wygenerowanie asercji
  Collections (`Dictionary Should Contain Key`, `Get From Dictionary`) do
  walidacji jej struktury.
- Uzyj AI do wygenerowania przykladowych danych testowych (payloadow JSON) do
  testow POST/PUT na podstawie opisu modelu danych.
- Poproś AI o przeksztalcenie polecenia `curl` na odpowiadajacy mu fragment
  .robot z RequestsLibrary (Create Session + odpowiedni keyword On Session).
- Wklej log bledu nieudanego testu API i poproś AI o wskazanie, czy problem
  lezy po stronie testu (zla asercja/URL) czy po stronie API (np. 500/timeout).

## Zadanie na dzis
Napisz suite korzystajacy z RequestsLibrary i Collections, ktory: utworzy
sesje do publicznego API (np. jsonplaceholder.typicode.com), wykona test GET
zwracajacy liste i zweryfikuje jej dlugosc oraz strukture pierwszego elementu,
wykona test POST tworzacy nowy zasob z walidacja kodu statusu (expected_status)
i zawartosci odpowiedzi, oraz dodatkowo test negatywny sprawdzajacy odpowiedz
API na zadanie o nieistniejacy zasob (np. status 404).

# Dzien 8 (2026-07-31, piatek) - Dane testowe i Data-Driven Testing z Templates

## 1. Temat dnia
Dzisiejszy temat to obsluga danych testowych oraz Data-Driven Testing (DDT)
w Robot Framework przy uzyciu sekcji `[Template]`. Zamiast pisac osobny Test
Case dla kazdego zestawu danych, definiujemy jeden szablonowy Keyword, a w
sekcji `*** Test Cases ***` podajemy tylko kolejne wiersze danych wejsciowych.
Znacznie skraca to testy i ulatwia utrzymanie logiki w jednym miejscu.

## 2. Kluczowe zasady i najlepsze praktyki
- `[Template]` w Test Case (lub globalnie w `*** Settings ***` jako
  `Test Template`) zamienia kazdy wiersz danych pod nazwa testu w osobne
  wywolanie wskazanego Keywordu - kazdy wiersz to de facto oddzielny "test".
- Kazdy wiersz danych w takim Test Case powinien miec czytelna nazwe
  (np. "Logowanie z pustym haslem"), bo to ona pojawia sie w log.html/report.html
  jako identyfikator konkretnego przypadku.
- Dane testowe warto trzymac oddzielnie od logiki: w plikach CSV/Excel
  wczytywanych przez `OperatingSystem`/biblioteki zewnetrzne, w zmiennych
  (`*** Variables ***`) lub w osobnym Resource file - Keyword szablonowy
  ma tylko przyjmowac argumenty, a nie zawierac dane na sztywno.
- Do parametryzacji wielu argumentow na wiersz uzywaj tabel z wyrownanymi
  kolumnami (dobra czytelnosc) oraz `...` do kontynuacji dlugich wierszy.
- Laczenie `[Template]` z `[Tags]` per wiersz (np. `[Tags]` w kolejnych
  liniach) pozwala selektywnie uruchamiac tylko wybrane przypadki danych.
- Gdy jeden wiersz danych zawiedzie, pozostale wiersze i tak sie wykonaja -
  to zaleta DDT (pelny raport wszystkich przypadkow), ale trzeba o tym
  pamietac projektujac asercje.

## 3. Przykladowy kod
```robotframework
*** Settings ***
Documentation     Przyklad Data-Driven Testing z uzyciem [Template].
Library           Collections

*** Test Cases ***
Walidacja logowania dla roznych danych
    [Template]    Sprawdz wynik logowania
    login=admin      haslo=admin123     oczekiwany=SUKCES
    login=admin      haslo=zlehaslo     oczekiwany=BLAD
    login=${EMPTY}   haslo=admin123     oczekiwany=BLAD
    login=admin      haslo=${EMPTY}     oczekiwany=BLAD
    login=${EMPTY}   haslo=${EMPTY}     oczekiwany=BLAD

*** Keywords ***
Sprawdz wynik logowania
    [Arguments]    ${login}    ${haslo}    ${oczekiwany}
    ${wynik}=    Zaloguj    ${login}    ${haslo}
    Should Be Equal    ${wynik}    ${oczekiwany}

Zaloguj
    [Arguments]    ${login}    ${haslo}
    IF    "${login}" == "" or "${haslo}" == ""
        RETURN    BLAD
    END
    IF    "${login}" == "admin" and "${haslo}" == "admin123"
        RETURN    SUKCES
    END
    RETURN    BLAD
```

Przyklad z danymi z pliku CSV (wczytanie i iteracja przez `FOR`):
```robotframework
*** Settings ***
Library    OperatingSystem
Library    String

*** Test Cases ***
Test z danymi z pliku CSV
    ${zawartosc}=    Get File    ${CURDIR}/dane_logowania.csv
    @{wiersze}=      Split To Lines    ${zawartosc}
    FOR    ${wiersz}    IN    @{wiersze}
        @{dane}=    Split String    ${wiersz}    ,
        Sprawdz wynik logowania    @{dane}
    END
```

## 4. Najczestsze bledy
- Wpisywanie danych testowych na sztywno wewnatrz Keywordu szablonowego
  zamiast przekazywania ich jako argumenty - traci sie caly sens DDT.
- Brak czytelnych nazw wierszy w Test Case z `[Template]` - w raporcie
  widac wtedy tylko nieopisane, trudne do zidentyfikowania przypadki.
- Mieszanie w jednym Template roznej liczby/kolejnosci argumentow w
  poszczegolnych wierszach, co prowadzi do myloncych bledow o niezgodnej
  liczbie parametrow.
- Ignorowanie faktu, ze kazdy wiersz to osobny "test" w raporcie - przy
  duzej liczbie danych log.html/report.html moze zrobic sie nieczytelny,
  jesli nie pogrupuje sie danych sensownie (np. po tagach).
- Brak walidacji formatu danych wejsciowych (np. z CSV) przed uzyciem ich
  w Keywordzie - literowka w danych zewnetrznych powoduje trudny do
  namierzenia falszywy blad testu.

## 5. Ulepszenia z AI
- Poproś AI o wygenerowanie kompletu przypadkow brzegowych (edge cases) do
  tabeli `[Template]` na podstawie opisu reguly biznesowej (np. walidacja
  formularza logowania czy rejestracji).
- Wklej istniejacy zbior danych testowych (np. arkusz/CSV) i poproś AI o
  przeksztalcenie go w gotowa tabele `[Template]` w skladni Robot Framework.
- Wykorzystaj AI do wygenerowania danych syntetycznych (np. losowe adresy
  email, numery telefonow, kombinacje pol) do zasilenia testow DDT.
- Poproś AI o zaproponowanie brakujacych kombinacji danych (macierz
  parametrow), ktore mogly zostac pominiete w reczne pisanej tabeli.
- Uzyj AI do przejrzenia istniejacego zestawu duplikatow Test Casow i
  zaproponowania ich konsolidacji w jeden Test Case z `[Template]`.

## Zadanie na dzis
Zamien trzy oddzielne, powtarzalne Test Case'y (np. testujace rejestracje
uzytkownika z roznymi danymi wejsciowymi) na jeden Test Case korzystajacy z
`[Template]`. Dodaj co najmniej 5 wierszy danych obejmujacych przypadki
pozytywne i negatywne (np. puste pole, zly format email, za krotkie haslo),
nadaj kazdemu wierszowi czytelna nazwe i uruchom test z flaga `--test`, aby
sprawdzic, ze kazdy wiersz jest widoczny jako osobny przypadek w raporcie.

# Dzien 9 (2026-08-01, sobota) - Tagowanie i selektywne uruchamianie testow

## 1. Temat dnia
Tagowanie testow ([Tags]) oraz selektywne uruchamianie ich przy pomocy flag
`--include` / `--exclude` / `--test` / `--suite` w Robot Framework.

## 2. Kluczowe zasady i najlepsze praktyki
- Tagi nadaje sie w [Tags] na poziomie Test Case lub globalnie przez
  Force Tags/Default Tags w sekcji *** Settings ***.
- Uzywaj krotkich, spojnych nazw tagow (np. smoke, regression, api, slow) -
  ustal konwencje nazewnictwa dla calego zespolu i trzymaj sie jej.
- Tagi mozna laczyc logicznie przy uruchamianiu: `--include tagA --exclude
  tagB` albo wyrazenia typu `smokeANDapi`.
- Warto tagowac testy wg priorytetu (critical/high/low), obszaru (login,
  checkout) i typu (smoke, regression, slow) - to umozliwia elastyczne
  odpalanie podzbiorow w CI/CD.
- Unikaj tagow "na wyrost" bez sensu biznesowego - kazdy tag powinien
  odpowiadac na pytanie "po co bede filtrowac tym tagiem".

## 3. Przyklad kodu (.robot)
```robotframework
*** Settings ***
Documentation     Przyklad tagowania testow logowania
Force Tags        regression

*** Test Cases ***
Poprawne logowanie
    [Documentation]    Test smoke - krytyczna sciezka logowania
    [Tags]    smoke    critical    login
    Log    Symulacja poprawnego logowania

Logowanie z blednym haslem
    [Tags]    negative    login
    Log    Symulacja logowania z blednym haslem

Logowanie - test wydajnosciowy
    [Tags]    slow    performance
    Log    Symulacja dlugotrwalego testu logowania
```

Uruchomienie tylko testow smoke:
```bash
robot --include smoke tests/
```

Uruchomienie regresji z pominieciem wolnych testow:
```bash
robot --include regression --exclude slow tests/
```

Uruchomienie po wyrazeniu logicznym (smoke ORAZ login):
```bash
robot --include smokeANDlogin tests/
```

## 4. Najczestsze bledy
- Niespojne nazwy tagow (np. "Smoke", "smoke", "SMOKE-TEST" jako rozne
  tagi) - RF traktuje je jako oddzielne wartosci, filtr nie zlapie wszystkich.
  Robot Framework normalizuje wielkosc liter/spacje przy porownaniu tagow,
  ale mieszanie konwencji (myslnik vs podkreslnik) i tak utrudnia utrzymanie.
- Brak dokumentacji tagow - nikt w zespole nie wie co dany tag oznacza.
- Tagowanie "na sztywno" pojedynczych testow zamiast uzycia Force
  Tags/Default Tags dla calego pliku, gdy tag dotyczy calej suity.
- Zbyt duza liczba unikalnych tagow bez planu - trudno potem filtrowac
  sensowne podzbiory testow.
- Mylenie --include/--exclude z selekcja po nazwie (--test, --suite) -
  to inne mechanizmy i mozna je laczyc, ale trzeba rozumiec roznice.

## 5. Ulepszenia z AI
- Poproszenie Claude/Copilot o zaproponowanie spojnej konwencji nazewnictwa
  tagow dla calego projektu na podstawie listy istniejacych testow.
- Wklejenie pliku .robot i poproszenie AI o audyt tagow: wykrycie
  duplikatow, literowek i niespojnosci (np. "smoke" vs "smoke-test").
- Generowanie komend CI (np. dla GitHub Actions) z odpowiednia kombinacja
  --include/--exclude na podstawie opisu "chce odpalac tylko smoke na PR,
  a pelna regresje w nocy".
- Automatyczne generowanie dokumentacji tagow (README/wiki) na podstawie
  analizy uzytych tagow w calym repozytorium testowym.
- Analiza logow z uruchomienia (log.html/output.xml) przez AI w celu
  zaproponowania, ktore testy warto oznaczyc jako "slow" lub "flaky" na
  podstawie czasu wykonania i historii wynikow.

# Dzien 10 (2026-08-02) - Resource files i modularizacja testow

## 1. Temat dnia
Pliki .resource (Resource files) oraz modularizacja projektu testowego - jak
dzielic wspolne slowa kluczowe, zmienne i importy na osobne pliki, aby testy
byly czytelne, ponownie uzywalne i latwe w utrzymaniu.

## 2. Kluczowe zasady i najlepsze praktyki
- Wspolne slowa kluczowe i zmienne wydzielaj do plikow z rozszerzeniem
  .resource (nie .robot) - jasno oddziela to "biblioteke" testowa od
  wykonywalnych przypadkow testowych.
- Importuj plik zasobow przez `Resource    sciezke/do/pliku.resource` w
  sekcji *** Settings *** - sciezki podawaj wzgledem lokalizacji biedzacego
  pliku (mozna uzyc `${CURDIR}` dla pewnosci niezaleznie od katalogu
  uruchomienia).
- Trzymaj strukture katalogow logicznie: np. `resources/` (keywordy wspolne),
  `resources/pages/` (Page Object - lokalizatory i akcje per strona/ekran),
  `tests/` (przypadki testowe), `data/` (dane testowe).
- Jeden plik .resource powinien miec jedna odpowiedzialnosc (np.
  `login_keywords.resource`, `api_common.resource`) - unikaj jednego
  "worka" ze wszystkimi keywordami calego projektu.
- Unikaj cyklicznych importow (plik A importuje B, B importuje A) - RF
  zglosi blad parsowania; planuj hierarchie importow od ogolu do szczegolu.

## 3. Przyklad kodu (.robot)
Plik `resources/login_keywords.resource`:
```robotframework
*** Settings ***
Documentation     Wspolne slowa kluczowe zwiazane z logowaniem.
Library           Collections

*** Variables ***
${VALID_USER}        standard_user
${VALID_PASSWORD}     secret_sekrit

*** Keywords ***
Zaloguj Uzytkownika
    [Arguments]    ${login}=${VALID_USER}    ${haslo}=${VALID_PASSWORD}
    Log    Logowanie jako: ${login}
    Set Suite Variable    ${AKTUALNY_UZYTKOWNIK}    ${login}

Uzytkownik Powinien Byc Zalogowany
    Should Not Be Empty    ${AKTUALNY_UZYTKOWNIK}
    Log    Zalogowany uzytkownik: ${AKTUALNY_UZYTKOWNIK}
```

Plik `tests/login_tests.robot`:
```robotframework
*** Settings ***
Documentation     Testy logowania korzystajace z modulu resource.
Resource          ${CURDIR}/../resources/login_keywords.resource

*** Test Cases ***
Poprawne logowanie standardowym uzytkownikiem
    [Tags]    smoke    login
    Zaloguj Uzytkownika
    Uzytkownik Powinien Byc Zalogowany

Logowanie innym uzytkownikiem
    [Tags]    login
    Zaloguj Uzytkownika    login=admin_user    haslo=admin_pass123
    Uzytkownik Powinien Byc Zalogowany
```

## 4. Najczestsze bledy
- Uzywanie rozszerzenia .robot dla plikow zasobow zamiast .resource - dziala,
  ale myli czytelnikow (plik .robot sugeruje wykonywalne testy).
- Sciezki wzgledne liczone od katalogu uruchomienia `robot`, a nie od
  lokalizacji pliku - powoduje bledy "Import failed" przy uruchamianiu z
  innego katalogu; lekarstwo to `${CURDIR}`.
- Nadmierne "spłaszczanie" - jeden gigantyczny resource ze wszystkimi
  keywordami projektu utrudnia znalezienie czegokolwiek i zwieksza ryzyko
  konfliktow nazw.
- Duplikowanie tych samych keywordow w kilku resource'ach zamiast wydzielenia
  wspolnego, bardziej ogolnego pliku bazowego.
- Brak Documentation w plikach .resource - kolejny czlonek zespolu nie wie,
  do czego sluzy dany modul bez czytania calego kodu.

## 5. Ulepszenia z AI
- Poproszenie Claude/Copilot o zaproponowanie podzialu istniejacego,
  rozroslego pliku .robot na osobne resource'y wedlug odpowiedzialnosci
  (logowanie, koszyk, platnosci).
- Wklejenie kilku plikow testowych i poproszenie AI o wykrycie duplikatow
  keywordow, ktore mozna wyciagnac do wspolnego resource.
- Generowanie szkieletu struktury katalogow projektu (resources/, tests/,
  data/) na podstawie opisu aplikacji, ktora bedzie testowana.
- Automatyczne generowanie Documentation dla plikow .resource na podstawie
  analizy uzytych w nich Keywords.
- Poproszenie AI o audyt importow (Resource) pod katem cyklicznych zaleznosci
  lub nieuzywanych/zbednych importow w projekcie.

## Zadanie na dzis
Wydziel z dowolnego posiadanego pliku .robot (lub z przykladu powyzej) co
najmniej dwa wspolne slowa kluczowe do osobnego pliku .resource, zaimportuj
go w pliku testowym przez `Resource    ${CURDIR}/...` i uruchom test, aby
sprawdzic, ze modularyzacja dziala poprawnie.

# Dzien 11 (2026-08-03) - Custom Keywords i tworzenie wlasnych bibliotek w Pythonie

## 1. Temat dnia
Tworzenie wlasnych slow kluczowych (Custom Keywords) - zarowno w plikach
.robot/.resource, jak i jako pelnoprawne biblioteki napisane w Pythonie -
gdy standardowe biblioteki nie wystarczaja do wyrazenia logiki testowej.

## 2. Kluczowe zasady i najlepsze praktyki
- Custom Keyword w RF-owym .resource wystarcza, gdy logika to zlozenie
  istniejacych keywordow; biblioteke w Pythonie pisz dopiero, gdy potrzebujesz
  wlasnych obliczen, integracji z zewnetrznym API/SDK albo wydajnosci
  niedostepnej w czystym RF.
- Kazda klasa biblioteki w Pythonie powinna miec atrybut
  `ROBOT_LIBRARY_SCOPE` ('GLOBAL', 'SUITE' lub 'TEST') - okresla on, jak
  dlugo zyje instancja biblioteki i czy stan jest dzielony miedzy testami.
- Metody publiczne klasy staja sie slowami kluczowymi automatycznie (nazwa
  metody `zaloguj_uzytkownika` -> keyword `Zaloguj Uzytkownika`) - metody
  pomocnicze, ktore NIE maja byc keywordem, poprzedzaj podkreslnikiem `_`.
- Dokumentuj kazdy keyword docstringiem - trafia on wprost do log.html/
  Libdoc i jest jedynym zrodlem wiedzy dla reszty zespolu bez czytania kodu.
- Rzucaj wyjatki (`raise AssertionError(...)`) zamiast zwracac True/False -
  RF traktuje kazdy wyjatek jako FAIL testu, co jest zgodne z konwencja
  asercji w calym frameworku.

## 3. Przyklad kodu
Biblioteka Pythona `libraries/CalculatorLibrary.py`:
```python
from robot.api.deco import keyword, library


@library(scope="TEST", auto_keywords=False)
class CalculatorLibrary:
    """Prosta biblioteka RF demonstrujaca wlasne slowa kluczowe."""

    def __init__(self):
        self._historia = []

    @keyword("Dodaj Liczby")
    def dodaj_liczby(self, a, b):
        """Dodaje dwie liczby i zapisuje wynik w historii operacji."""
        wynik = float(a) + float(b)
        self._historia.append(wynik)
        return wynik

    @keyword("Ostatni Wynik Powinien Byc Rowny")
    def ostatni_wynik_powinien_byc_rowny(self, oczekiwany):
        if not self._historia:
            raise AssertionError("Brak zapisanej historii operacji.")
        ostatni = self._historia[-1]
        if ostatni != float(oczekiwany):
            raise AssertionError(
                f"Oczekiwano {oczekiwany}, otrzymano {ostatni}"
            )
```

Uzycie w pliku testowym `tests/calculator_tests.robot`:
```robotframework
*** Settings ***
Documentation     Test wlasnej biblioteki Pythona z zestawem keywordow.
Library           ${CURDIR}/../libraries/CalculatorLibrary.py

*** Test Cases ***
Dodawanie dwoch liczb dodatnich
    [Tags]    unit    custom-library
    Dodaj Liczby    3    4
    Ostatni Wynik Powinien Byc Rowny    7

*** Keywords ***
Zaloguj I Zweryfikuj Naglowek
    [Documentation]    Przyklad keyworda RF zlozonego z innych keywordow.
    [Arguments]    ${login}
    Log    Logowanie jako ${login}
    Page Should Contain    Witaj, ${login}
```

## 4. Najczestsze bledy
- Brak `ROBOT_LIBRARY_SCOPE` - domyslnie kazda instancja zyje tylko na czas
  jednego testu (TEST), co bywa zaskoczeniem, gdy oczekuje sie stanu
  wspoldzielonego w calym suite.
- Zwracanie `False`/komunikatu bledu zamiast rzucenia wyjatku - test konczy
  sie PASS mimo faktycznej porazki logicznej.
- Nazywanie metod pomocniczych bez podkreslnika `_` - przypadkowo staja sie
  publicznymi keywordami i zaśmiecaja liste dostepnych slow kluczowych.
- Mieszanie logiki biznesowej z asercjami w jednym keywordzie - utrudnia to
  ponowne uzycie (raz chcemy tylko pobrac wartosc, raz od razu ja zweryfikowac).
- Brak testow jednostkowych dla samej biblioteki Pythona - bledy w keywordach
  wychodza dopiero na duzych, kosztownych testach E2E.

## 5. Ulepszenia z AI
- Poproś Claude/Copilot o wygenerowanie szkieletu klasy biblioteki RF (z
  `ROBOT_LIBRARY_SCOPE`, dekoratorem `@keyword`, docstringami) na podstawie
  opisu potrzebnej funkcjonalnosci w jezyku naturalnym.
- Wklej istniejacy, rozrosniety Custom Keyword napisany w .robot i poproś AI
  o ocene, czy powinien zostac przepisany na biblioteke Pythona (np. ze
  wzgledu na zlozonosc logiki lub potrzebe obslugi wyjatkow).
- Uzyj AI do wygenerowania testow jednostkowych (pytest) dla wlasnej
  biblioteki Pythona, niezaleznie od testow .robot, ktore z niej korzystaja.
- Poproś o wygenerowanie dokumentacji Libdoc/README dla biblioteki na
  podstawie kodu zrodlowego, wraz z przykladami uzycia kazdego keyworda.
- Wykorzystaj AI do przegladu nazewnictwa keywordow pod katem spojnosci
  (np. czy wszystkie asercje zaczynaja sie od "Powinien/Powinna Byc").

## Zadanie na dzis
Napisz prosta biblioteke Pythona z co najmniej dwoma slowami kluczowymi
(jedno wykonujace operacje, drugie weryfikujace jej wynik przez rzucenie
wyjatku przy niepowodzeniu), zaimportuj ja w pliku .robot przez
`Library    ${CURDIR}/...` i uruchom test potwierdzajacy, ze oba keywordy
dzialaja poprawnie.

# Dzien 12 (2026-08-04) - Raportowanie i logi (log.html, report.html)

## 1. Temat dnia
Jak Robot Framework generuje wyniki testow - roznica miedzy output.xml,
log.html i report.html, sterowanie poziomem szczegolowosci logu oraz
dolaczanie dodatkowych informacji (zrzuty ekranu, wlasne wpisy) do raportu.

## 2. Kluczowe zasady i najlepsze praktyki
- output.xml to zrodlo prawdy - zawiera wszystkie dane z przebiegu testow;
  log.html i report.html sa generowane na jego podstawie (recznie przez
  narzedzie `rebot`, albo automatycznie po kazdym uruchomieniu `robot`).
- report.html to podsumowanie wysokiego poziomu (statystyki, tagi, PASS/FAIL
  per suite) - log.html to szczegolowy, klikalny zapis kazdego kroku i
  slowa kluczowego, wraz z argumentami i wartosciami zwracanymi.
- Poziom logowania ustawiaj przez `--loglevel` (domyslnie INFO) - w CI
  warto uzywac WARN/INFO, a szczegoly DEBUG/TRACE wlaczac tylko przy
  diagnozowaniu konkretnego problemu, bo TRACE potrafi wygenerowac
  ogromne pliki.
- Do wlasnych wpisow w logu uzywaj `Log` / `Log To Console` z jawnym
  poziomem (`Log    Wiadomosc    level=DEBUG`), a nie tylko domyslnego
  INFO - ulatwia to filtrowanie logu po fakcie.
- Nigdy nie loguj sekretow (hasel, tokenow) w postaci jawnej - RF domyslnie
  nie maskuje wartosci; jesli trzeba, uzyj `Log    ${haslo}    level=NONE`
  albo argumentu `--variable HASLO:*****` przy wywolaniu, ewentualnie
  wlasnej logiki maskujacej w Custom Keywordzie.

## 3. Przyklad kodu
```robotframework
*** Settings ***
Documentation     Przyklad logowania wlasnych informacji i zrzutu ekranu.
Library           OperatingSystem

*** Test Cases ***
Logowanie wlasnych wpisow do log.html
    [Documentation]    Pokazuje rozne poziomy logowania i Log To Console.
    [Tags]    reporting
    Log    Rozpoczynam test logowania danych    level=INFO
    Log    Szczegoly techniczne widoczne tylko przy --loglevel DEBUG    level=DEBUG
    Log To Console    Ta linia trafia od razu na konsole, nie tylko do logu
    Log Many    Wpis pierwszy    Wpis drugi    Wpis trzeci

Zapis zrzutu przy niepowodzeniu
    [Documentation]    Wymusza blad, aby pokazac wpis FAIL w log.html.
    [Tags]    reporting
    ${plik_istnieje}=    Run Keyword And Return Status
    ...    File Should Exist    ${CURDIR}/brak_takiego_pliku.txt
    Run Keyword If    not ${plik_istnieje}
    ...    Log    Plik nie istnieje - oczekiwane w tym przykladzie    level=WARN
    Should Be True    ${plik_istnieje}
    ...    msg=Plik testowy powinien istniec przed dalszymi krokami
```

Przydatne polecenia CLI do pracy z wynikami (poza kodem .robot):
```
robot --loglevel DEBUG --outputdir results tests/
rebot --merge --output merged.xml results/output1.xml results/output2.xml
rebot --log log.html --report report.html --loglevel WARN results/output.xml
```

## 4. Najczestsze bledy
- Ustawianie `--loglevel TRACE` na stale w CI - logi robia sie ogromne i
  ciezkie do przegladania, a build spowalnia przez sam zapis na dysk.
- Logowanie hasel/tokenow wprost w `Log` lub w argumentach keywordow -
  trafiaja one do log.html w postaci jawnej i moga wyciec przez artefakty CI.
- Mylenie report.html z log.html - szukanie szczegolow bledu w report.html,
  gdzie jest tylko podsumowanie, zamiast w log.html.
- Nieprzechowywanie output.xml jako artefaktu CI - bez niego nie da sie
  pozniej wygenerowac log.html/report.html ani zmergowac wynikow przez rebot.
- Ignorowanie kolorowych sekcji WARN/ERROR w konsoli podczas przebiegu -
  test moze przejsc (PASS), a mimo to zawierac istotne ostrzezenia w logu.

## 5. Ulepszenia z AI
- Wklejenie fragmentu log.html (lub tresci bledu z konsoli) do Claude/
  ChatGPT z prosba o wskazanie najbardziej prawdopodobnej przyczyny FAIL-a
  na podstawie stack trace'u i argumentow keywordu.
- Poproszenie AI o wygenerowanie czytelnego podsumowania z duzego
  output.xml/report.html (np. "ktore suity maja najwiecej FAIL, jaki jest
  sredni czas trwania testu") zamiast recznego przegladania.
- Uzycie AI do zaproponowania miejsc w kodzie testowym, gdzie warto dodac
  `Log`/`Log To Console` z konkretnym poziomem, aby ulatwic przyszle
  debugowanie bez zasmiecania logu w trybie normalnym.
- Poproszenie AI o przejrzenie testow pod katem logowania danych
  wrazliwych (hasel, tokenow, PII) i zaproponowanie sposobu ich maskowania.
- Wygenerowanie przez AI polecenia `rebot` do zmergowania wynikow z wielu
  rownoleglych przebiegow (np. z Pabot) w jeden spojny log.html/report.html.

## Zadanie na dzis
Uruchom dowolny test z parametrem `--loglevel DEBUG`, dodaj do niego wlasny
`Log` na poziomie DEBUG oraz `Log To Console`, a nastepnie porownaj, co
widac w log.html przy `--loglevel INFO` a co dodatkowo pojawia sie przy
`--loglevel DEBUG`.
